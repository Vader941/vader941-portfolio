Productivity Tracking

From a barcode-scanning prototype to an approach used across 108 studios.

We had productivity targets, but counting items didn't tell us how much work those items required. Someone handling complex products could miss the target while someone handling easier products went right past it.

I worked with preparation and styling leads to develop standards based on the complexity of the work, using existing targets and observed processing times. Then I built an Excel and VBA prototype using barcode scanners to put that approach into practice. Employees scanned a complexity category, and we audited those selections to keep the measurements useful.

The prototype informed a web application adopted by 108 studios globally. Development and management determined how to automate complexity classification using product catalog data. I worked with developers to keep the productivity calculations adaptable because different studios handled different product lines and needed their own standards.

The resulting data supported analysis through Tableau. Combined with incoming-item forecasts from another process, it helped teams plan capacity around the mix of work coming in. It also helped identify patterns and workflow bottlenecks. The initial focus was studio and department performance; individual performance tracking developed later.

Inbound and Outbound Automation

Faster receiving, fewer errors, and checks before items returned to warehouse inventory.

An item arriving for product imaging needed more than a receiving scan. Employees had to move inventory between virtual holding bins, check ownership and inventory status, look up imaging requirements and request notes, and receive the item into an imaging project. That meant working across several intranet screens and tools.

I built an inbound tool that brought those steps together. An employee could scan the item once, and the application gathered the information and performed the system actions in the background. It then showed where the item needed to go physically, based on ownership and product department.

The difference was immediately noticeable. Manually processing an incoming item could take roughly two to five minutes, depending on ownership, request notes, and other complications. With the tool, most items took about eight to fifteen seconds. Employees spent less time clicking through systems and could keep the physical work moving.

When something couldn't be processed normally, the tool alerted the employee and emailed the person responsible for resolving it. The item could be set aside for research while that person investigated, sometimes without needing it in hand. It worked as a practical exception-handling system alongside the automated process.

The outbound tool handled the return to warehouse inventory and closed the imaging project. It checked that completed images were present and looked for flags in a separate database. If someone had identified a problem while an item was waiting to be repackaged, they could flag it rather than search through hundreds of items. The tool caught it at outbound and directed the employee to the person who needed it.

Together, these tools helped reduce the studio's measured defect rate from about 2.3% to 0.05%. That measurement covered inbound and outbound, where the studio's work connected with warehouse inventory.

Stock Trading Capstone

An ongoing three-person Information Technology capstone at Arizona State University.

I lead a three-person team building a mock stock trading system in Django. The application brings together accounts, simulated stock prices, buying and selling, portfolio tracking, and transaction history.

My role includes turning the project scope into requirements and a system design, breaking the work into assignments, and coordinating how the pieces come together. As development progresses, I review pull requests, help teammates work through issues, and check that our implementation stays consistent with the design.

I also contribute code, including the market simulation, price history, and market exception calendar. A big part of the work is making sure features developed by different people follow the same rules and work together as one system.

The project is ongoing as part of my Information Technology capstone at Arizona State University.

L’Oréal Beauty Routines

AI-powered routine builder and product advisor

L’Oréal Beauty Routines lets visitors build a skincare or beauty routine around real products and then chat with a personal beauty advisor powered by OpenAI. Users can filter products by category, select the ones they care about, and ask detailed questions about when and how to use everything together.

Under the hood, I wired a static GitHub Pages front end to a Cloudflare Worker that securely calls the OpenAI API. The app keeps track of selected products in localStorage, so people can come back later and pick up where they left off.

Tech highlights

  • HTML, modern CSS, and vanilla JavaScript for the UI and product grid.
  • OpenAI API access proxied through a Cloudflare Worker so my API key never lives in the browser.
  • Conversation history and product context passed to the model for smarter, more personalized responses.
  • Local persistence of selected products using localStorage so sessions feel continuous.

Space Explorer

Daily images and facts from NASA’s archive

Space Explorer pulls in NASA’s Astronomy Picture of the Day over a custom date range and presents it in a clean, readable gallery. Set your dates, then scroll through high-resolution imagery with the official explanations alongside. You can even check what NASA published on your birthday.

This project was my way of getting comfortable with third-party APIs, error handling, and building a UI that feels good whether you are on a laptop or a phone.

Tech highlights

  • Fetches imagery and metadata from the official NASA API.
  • Responsive layout that adapts from a single-column mobile view to a richer desktop layout.
  • Date-range selection with basic validation and friendly error messages.
  • Hosted on GitHub Pages, using a Cloudflare Worker where needed to keep keys safe.

Pipeline to Hope

Awareness-driven puzzle game for clean water

Pipeline to Hope is a timed pipe-connecting game built for Charity: Water. The goal is simple: connect the pipes and get clean water to the village before the clock runs out. Behind the scenes, there is grid logic, collision checking, and state management doing the work.

I built this as a prototype to explore how simple games can support education and awareness, and to stretch my JavaScript skills beyond basic forms and DOM manipulation.

Tech highlights

  • Custom game loop and board logic written in vanilla JavaScript.
  • Responsive layout so the game is playable on both desktop and mobile.
  • Configurable difficulty and timing so the experience can be tuned.
